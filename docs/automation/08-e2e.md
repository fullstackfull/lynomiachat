# Lynomia Automation: end-to-end verification

One run, on the production configuration, through the browser, the API, a real store and a real job worker:
`docs/automation/e2e/run.sh <out> <scratch>` (results: [`e2e/results/`](e2e/results/), screenshots:
[`screenshots/`](screenshots/)).

## Setup

| Part | What |
|---|---|
| App | the working tree's production build (`bin/vite build`), `RAILS_ENV=production`, plain `rails s` |
| Worker | Sidekiq (`config/sidekiq.yml`), same image and environment, restarted once with `SAFE_FETCH_ALLOW_PRIVATE_NETWORK=true` (`e2e/worker.sh`) |
| Store | the disposable local WooCommerce test store A1, connected with its Read key; its order 23 (Omar Khalil, SAR 135, pending) moved with wp-cli and put back to pending |
| Providers | Salla, Zid, Shopify switched off (the production gate) |
| Accounts | Lynomia Demo A (Commerce, CRM, Automations), Lynomia Demo B (its own shared audience, store and team, which A's rules must never reach) |
| n8n | a local HTTP catcher on `127.0.0.1:3901` standing in for an n8n webhook node |
| Control | `e2e/ctl.rb` (setup, state, audiences, kill switch, teardown) |

## Flow and checks

1. **Setup**: store A1 connected; Demo B has its own audience, store and team.
2. **Baseline**: the agent opens Omar's conversation; Commerce reads his orders (order 23 pending, unpaid); no rule
   runs (first read = baseline).
3. **Shared audience**: the administrator filters Contacts by *Visible spend (SAR) > 1*, saves *VIP buyers* with
   *Share with the whole account*; it is stored `shared`, listed as *VIP buyers · Shared*.
4. **Agents read-only**: the agent sees *VIP buyers · Shared*, no delete button, the read-only note; the API refuses an
   agent's share, rename and delete (401).
5. **Triggers**: the event list has a *Conversations* group (Chatwoot's 5) and a *Commerce* group (7); choosing
   *Commerce order paid* shows when it runs and that customer messages are not available.
6. **Conditions**: the attribute picker has Chatwoot's fields, then *Audience* (*Contact audience*, "Is in") and
   *Commerce* (*Order store*, *Order store platform*, the Audience Commerce fields); only shared audiences are offered
   (the admin's personal *My follow-ups* is not).
7. **Actions**: Chatwoot's list without *Send a Message* / *Send Attachment* on a Commerce trigger.
8. **Rule saved** as an ordinary `automation_rules` row: `commerce_order_paid`, `contact_audience = [VIP]` AND
   `commerce_event_provider = woocommerce`, `add_label paid-vip`, `send_webhook_event http://127.0.0.1:3901/n8n/lynomia`.
9. **API refusals (422)**: personal audience, Demo B's audience, Demo B's store, `send_message` on a Commerce trigger,
   an event condition on `conversation_created`, an injected platform value.
10. **Permissions and accounts**: an agent cannot create a rule (401); Demo B cannot read Demo A's rule (401) nor use
    Demo A's audience in its own rule (422).
11. **Real event**: wp-cli sets order 23 to processing on the store; the agent's Refresh reads it as paid (one store
    call); the worker runs the rule: `paid-vip` on Omar's latest conversation.
12. **Same event, other rule**: "Contact audience is not in VIP buyers" → `skipped`.
13. **Demo B's team and agent** in a Demo A rule (accepted by Chatwoot's API) are never applied: the conversation
    keeps its team and assignee.
14. **SSRF as shipped**: the webhook to `127.0.0.1` is refused by SafeFetch on the worker; nothing reaches the catcher.
15. **Execution log**: one line per rule and event with ids, trigger, outcome, duration and actions; no contact name,
    e-mail or phone in any line.
16. **No rule, no run**: order 23 back to pending, read after the cooldown: an `updated` change no rule listens to
    runs nothing.
17. **Self-hosted n8n**: worker restarted with `SAFE_FETCH_ALLOW_PRIVATE_NETWORK=true`; order 23 paid again, read: the
    catcher receives one POST, `event: automation_event.commerce_order_paid`, the conversation, and `commerce: { event,
    store_id, provider: woocommerce, order: { number: 23, status: processing, payment_status: paid } }`.
18. **No secret in the webhook**: the received body has neither the store key nor its secret.
19. **Cached read**: the agent's next read (from cache) runs nothing and sends nothing.
20. **Store restored**: order 23 is pending again.
21. **Dependency blocking**: the admin's filter panel says the audience is used by 2 active rules; deleting it in the
    UI shows "This audience is used by 2 automation rules"; API delete and unshare answer 422; the audience stays.
22. **Kill switch**: `LYNOMIA_AUTOMATION_EXTENSIONS_ENABLED=false` (installation config) refuses a rule with an audience
    condition; a plain Chatwoot rule still saves.
23. **Arabic, desktop**: trigger groups, the Commerce note and the Audience / Commerce condition names in Arabic.
24. **Arabic, 390 px**: right to left; the rule builder and its note inside the screen.
25. **English, 390 px**: the rule builder and its note inside the screen.
26. **No store key or secret** in any response the browser received.
27. **No uncaught page errors.**
28. **Teardown**: stores, audiences, rules and the run's label removed.

## Result

**28/28 passed** ([`e2e/results/e2e_automation.txt`](e2e/results/e2e_automation.txt),
[`automation_e2e_results.json`](e2e/results/automation_e2e_results.json)). The worker's Lynomia log lines of the run are
in [`automation_log_lines.txt`](e2e/results/automation_log_lines.txt): two paid events (one per worker mode), three
rules each (`executed`, `skipped`, `executed`), and the SSRF refusal of the first webhook.

Found and fixed by this E2E: in Arabic, Chatwoot's side panels (the rule builder among them) opened with zero height
below the screen. A Lynomia sidebar style, `:global([dir='rtl']) .sidebar-nav :deep(a:hover)`, compiled to a global
`[dir=rtl] { transform: translateX(-3px) }` (Vue's `:global(X) …` keeps only `X`), so every right-to-left wrapper,
including the teleported panel's, became the containing block of its `position: fixed` children. The selector is now
`[dir='rtl'] .sidebar-nav :deep(a:hover)` (`Sidebar.vue`): only the sidebar's links move on hover, as intended.
