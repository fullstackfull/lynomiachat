The first Automation run gave 27/28: its "no uncaught page errors" check collected
`Key already exists in the object store`, then an aborted transaction, in the administrator's browser. It reproduced on
this build and not on the one before it, so it was tracked down rather than re-run.

**Cause (class A, a defect in Chatwoot's cache, fixed here).** `DataManager#push` wrote with IndexedDB `add`, which
throws when the key is already there. Two fetches of the same cached model (`inbox`, `label`, `team`, `canned_response`)
can be in flight at once — the sidebar and a page both refetch after a cache key changes; each runs `replace`
(`clear`, then write every row), so the writes interleave, the second `add` throws `ConstraintError`, **the transaction
aborts and the store is left empty**, which the page surfaces as an uncaught error. Nothing in this phase fetches or
caches those models (`CampaignRecipients` reads the `customViews` store, whose client is not cache-enabled;
`ContactListHeaderWrapper` passes one more prop), but the extra `campaigns_count` the shared-audience JSON now computes
shifts response timing enough to make the race fire. A page-error probe over the segment page, its filter, the automation
list and the campaigns page found 0 errors on both builds, which is why the fix is in the writer and not in a page.

The write is now `put` (upsert), so a racing replace keeps the full collection instead of aborting
(`DataManager.js`, with a Vitest for two concurrent replaces). Automation E2E on the fixed build: **28/28**.

## 5. Deployment and rollback

| | |
|---|---|
| Migrations | **none**. `campaigns.audience` is an existing jsonb column; `Audience` entries are a new entry type in it |
| Deploy | code and the frontend build only (`pnpm install --frozen-lockfile` before `pnpm vite build`, as the Flow Builder release already requires) |
| Feature flag | none added. Shared audiences already exist per account; a campaign simply offers them |
| Rollback (code back, data kept) | the previous version reads `campaigns.audience` and keeps only `type == 'Label'` entries, so a campaign that was still to send would go to its labels alone — **to nobody if it listed audiences only**. Before rolling back, delete the one-off campaigns that are `active` and reference an audience (`Campaign.one_off.active.where("audience @> ?", [{ type: 'Audience' }].to_json)`), and recreate them afterwards; campaigns already `completed` are unaffected, as are label-only campaigns |
| Rollback (data back) | nothing to undo: no table, column or row was added |
