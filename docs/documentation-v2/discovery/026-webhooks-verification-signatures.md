## 2. The rules

### 2.1 The verification handshake

When the Webhooks product is configured in the App Dashboard (or a subscription is created through
`/app/subscriptions`), Meta sends a **`GET`** request to the callback URL with three query parameters (S1, S5, S4, S10):

| Parameter | Value Meta sends | Stated type |
|---|---|---|
| `hub.mode` | always `subscribe` (S1, S4, S5) | string |
| `hub.challenge` | the value the endpoint must echo | S1 and S4 call it "an `int`"; S5 calls it "a random string generated by Meta" and shows `1158201444`. **Inconsistent across pages** |
| `hub.verify_token` | the string the developer typed into the Verify Token field in the App Dashboard (S1, S5) | string |

The endpoint must compare `hub.verify_token` against the value it stored and then **respond with the
`hub.challenge` value**. Only S5 states the status code: "respond with HTTP status `200` and the `hub.challenge`
value". S1, S4 and S10 state the echo requirement without naming a status code. **No page in this pass states a
required `Content-Type` for the handshake response.**

On a token mismatch, S5 says to "respond with a 400-level HTTP status code, or anything other than status `200`" —
i.e. the exact code is the developer's choice. The Messenger and Instagram samples use `403` (S3, S4).

**What Meta does when verification fails** (S5, explicit): "Meta will consider your webhook endpoint unverified"
and **webhooks will not be sent**. S1 adds only that the App Dashboard "will indicate if your endpoint validated
the request correctly" and that `/app/subscriptions` returns success or failure. **Whether Meta re-attempts the
verification GET on its own, and for how long, is not stated on any page read.** The documented recovery is
manual: fix the endpoint and save the configuration again.

### 2.2 Transport: HTTPS, certificates, mTLS

- The endpoint must accept HTTPS and have "a valid TLS or SSL digital security certificate, correctly configured
  and installed" (S1, S2, S5, S10).
- "**Self-signed certificates are not supported.**" — stated verbatim on S1, S2, S3/S4, S5 and S10.
- **No page states a required port, a minimum TLS version, or a cipher policy.** Not stated.
- **mTLS is optional** (S1, S6). S1 gives the operative detail: Meta presents a client certificate plus its
  signing intermediate; the server (or load balancer) must trust the CA file **`meta-outbound-api-ca-2025-12.pem`**
  and then verify the common name **`client.webhooks.fbclientcerts.com`**. S1 states this certificate "replaces the
  previous DigiCert-signed certificate, which expired on **April 15, 2026**". S1 shows nginx
  (`ssl_verify_client on;`, `ssl_client_certificate`, `ssl_verify_depth 3;`) and AWS ALB (read the CN from
  `X-Amzn-Mtls-Clientcert-Subject`) configurations. S14 (observational) adds that the CA transition began
  **March 31, 2026** and that the new leaf keeps the same CN.
- **Scope of mTLS enablement is stated inconsistently**: S1 says it applies "once you enable it on your WhatsApp
  Business Account subscription"; S5 says mTLS "is enabled per application, not at the WABA or phone number level".
  Recorded as an ambiguity, not resolved (§6).
- S6 mentions allow-listing Meta's IP addresses as an alternative, while warning that Meta "periodically changes
  its IP addresses" and recommending mTLS instead. **No IP list is quoted here and none should be hard-coded.**

### 2.3 Payload signing — `X-Hub-Signature-256`

| Aspect | What Meta states | Source |
|---|---|---|
| Header name | `X-Hub-Signature-256` | S1, S3/S4, S5, S10 |
| Value format | `sha256=` followed by the hash — S5 writes it as `sha256=<SHA256_PAYLOAD_HASH>` | S1, S5 |
| Algorithm | HMAC-SHA256. S4's sample: `crypto.createHmac("sha256", config.appSecret).update(buf).digest("hex")`. S5 names HMAC-SHA256 explicitly | S4, S5 |
| Key | **the app's App Secret** | S1, S3/S4, S5, S10 |
| Bytes signed | S5 says only "the JSON payload" / "post body payload". **S4 is the only page that is specific, and it specifies something unusual**: the signature is generated from an **escaped-unicode** version of the payload with **lowercase hex digits**, and hashing the decoded bytes "produces a different signature" (its example: `äöå` must be escaped to `äöå`). S4's own sample code nevertheless hashes the raw request buffer and does not perform any escaping | S4, S5 |
| Encoding | lowercase hex in every example; S5 does not state a case requirement | S4, S5 |
| Comparison | "compare your signature to the signature in the `X-Hub-Signature-256` header (everything after `sha256=`)". **No Meta page read recommends a constant-time comparison**; S4's sample uses a plain `!=` | S1, S4, S5 |
| Obligation | Optional but recommended: S1 — "You don't have to validate the payload, but you should"; S4 — "we strongly recommend that you do" | S1, S4 |
| Behaviour when signature is absent or wrong | **Not stated.** No page says whether Meta retries a request the endpoint rejected for a bad signature, or whether rejecting with 401 counts as a delivery failure | — |

### 2.4 The response Meta expects, and timing

- "Your endpoint should respond to all Event Notifications with `200 OK HTTPS`" (S1, S10). S5: respond with HTTP
  200 for a valid payload, and "a 400-level status, or anything other than status 200" for an invalid one.
- S6 defines failure by exclusion: a retry happens when the endpoint returns "an HTTP status code other than 200"
  or delivery fails for another reason.
- **Timing: only the Messenger pages state a deadline — "within 5 or less seconds" (S3, S4).** S1, S5, S6, S9 and
  S10 state **no timeout at all**. So the 5-second figure is normative for Messenger and **must not be presented
  as a platform-wide number**; it is simply the only number Meta states, and it is the safe design target.
- S4 notes a tension in Meta's own guidance: it tells you to send the 200 only after processing completes, while
  also requiring a response inside 5 seconds. What happens after a timeout, beyond retrying, is not stated.
- S4's sample returns `404` for notifications whose object is not a Page.

### 2.5 Retries, and when Meta gives up

This is the single most contradictory area in Meta's documentation, and both sides are normative.

| Source | Product | Stated retry behaviour | Give-up point |
|---|---|---|---|
| S1 | Graph API (generic) | "If any update sent to your server fails, we will retry immediately, then try a few more times with decreasing frequency over the next **36 hours**" | "Unacknowledged responses will be dropped after **36 hours**" |
| S10 | Instagram Platform | identical wording, **36 hours** | dropped after **36 hours** |
| S5 | WhatsApp Cloud API | retried immediately, then several more times "with decreasing frequency over the next **7 days**" | "Unacknowledged responses will be dropped after **7 days**" |
| S6 | WhatsApp Cloud API | "retries delivery with decreasing frequency until the request succeeds, for up to **7 days**" | implied at 7 days |
| S3/S4 | Messenger Platform | "we will immediately try a few more times" — **no window given** | not stated; superseded by the disable timeline below |

**No page states a retry count, a backoff formula, or the individual retry intervals.** "A few more times with
decreasing frequency" is the whole of it. Any specific number of retries is an invention.

**Disabling a subscription** is documented only for Messenger/Instagram-via-Messenger (S3, S4): after **15 minutes**
of failure "an alert is sent to your developer account"; after **1 hour** of continued failure you receive a
"**Webhooks Disabled**" alert and **the app is unsubscribed from the Page or Instagram Professional account's
webhooks**, and you must resubscribe after fixing the problem. **For WhatsApp, no equivalent disable behaviour is
documented anywhere read** — S5 and S6 describe only retries up to 7 days. Whether a WhatsApp subscription is ever
auto-disabled is **not stated**.

S6 adds one fact with multi-app consequences: retries "are sent to all apps subscribed to the WABA's webhooks and
their relevant fields" — a redelivery is not scoped to the app that failed.

S5 also states there are **no APIs for fetching past webhook data**, so anything not persisted on receipt is gone.

### 2.6 Ordering

**No page read states a positive ordering guarantee.** S3/S4 explicitly deny it: when several messages arrive
during an outage they "may not be delivered in the order they were sent", and the documented remedy is to order by
the webhook `timestamp` field. S1, S2, S5, S6, S9 and S10 say nothing about ordering at all. Ordering outside an
outage is **not stated** even on the Messenger pages.

Treat webhook delivery as **unordered**. That is the only position the documentation supports.

### 2.7 Duplicates and deduplication

Duplicates are acknowledged on every platform: retries "can result in duplicate webhook notifications" (S6), and
"Your server should handle deduplication in these cases" (S1, S5, S10, and S3/S4).

**Meta nominates no deduplication key anywhere.** That is the key gap in this area. What the payloads do carry
(S9, S3/S4):

| Identifier | Where | Usable as a dedup key? |
|---|---|---|
| `messages[].id` (a `wamid.`-prefixed WhatsApp message ID) | WhatsApp inbound | Plausible per-message key. **Meta does not say so.** |
| `statuses[].id` (also `wamid.`) | WhatsApp outbound status | **Not sufficient alone.** S9 states "each outgoing message can have up to three separate webhooks" — sent, delivered, read — all carrying the same `id`. A dedup key for statuses needs `id` + `status` (and arguably `timestamp`) |
| `entry[].id` | WhatsApp (WABA ID), Messenger (Page ID) | an object ID, not an event ID |
| `mid` | Messenger message events | present in examples; S3/S4 do **not** nominate it for dedup |
| `timestamp` | `entry[].time`, messaging events, `statuses[].timestamp` | nominated for **ordering** (S3/S4), not for identity |

Anything stronger than the above — "Meta recommends deduplicating on X" — is unsupported.

### 2.8 Batching

- "Event Notifications are aggregated and sent in a batch with a maximum of **1000 updates**" (S1, S5, S10).
- "However batching cannot be guaranteed so be sure to adjust your servers to handle each Webhook individually"
  (S1, S5).
- S1's payload table: "Multiple changes from different objects that are of the same type may be batched together" —
  i.e. one request can carry entries for **different WABAs/Pages**, so an endpoint must not assume one request
  equals one account.
- S3/S4: "The `entry` array contains one or more event objects, each with a `messaging` array of individual events."
- **Maximum payload size: 3 MB** (S6, S7). No size limit is stated on S1, S3/S4 or S10.
- S9's examples each show a single `entry`/`changes`/`messages` element and the page says nothing about batching;
  the arrays are the contract, the single-element examples are not.

### 2.9 Subscription routing, overrides and dev mode (what decides where a webhook lands)

S8 is load-bearing for any multi-tenant product:

- Resolution order for a WhatsApp webhook: the **business phone number's** override, then the **WABA's** override,
  then **the app's callback URL**.
- Fields that **support** overrides: `messages`, `message_echoes`, `calls`, `consumer_profile`,
  `messaging_handovers`, `group_lifecycle_update`, `group_participants_update`, `group_settings_update`,
  `group_status_update`, `smb_message_echoes`, `smb_app_state_sync`, `history`, `account_settings_update`.
- Fields that **do not** support overrides, and are therefore "always delivered to your app's default callback
  URL": the template fields `message_template_status_update`, `message_template_quality_update`,
  `message_template_components_update`, `template_category_update`; and the account-level fields `account_update`,
  `account_review_update`, `account_alerts`.
- Each override "requires its own `verify_token`" (marked Required). **Whether Meta runs the same `hub.challenge`
  GET against an override URL is not stated** on S8, though it links to the verification-requests documentation.
- Permissions (S6/S7): `whatsapp_business_messaging` for the `messages` field, `whatsapp_business_management` for
  the others.
- Dev mode (S2, S6): apps in development mode receive only test notifications or notifications from people with a
  role on the app, and "some webhooks will not be sent if your app is in Dev mode". The app must be Live.

directions plus `errors[]` arrays carried *inside* payloads (those codes belong to agents 005/007, not here).
Nothing in this table is invented; `not stated` means Meta does not say.

| code | subcode | title as Meta words it | what it means | what the business can do | what the end user sees | source row |

| n/a (HTTP non-200) | — | "an HTTP status code other than 200" | delivery failed; retries begin | restore the endpoint inside the retry window | delayed inbound messages, then permanent loss after the window | S6 |

## 5. Version and deprecation notes

- Webhooks themselves are not versioned in the documentation; the Graph API version appears only on the
  `/app/subscriptions` call used to create a subscription (S1, S2).
- **Meta has migrated these docs to a new path family.** WhatsApp webhooks now live under
  `developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/**` (S5, S6, S8) while
  `/docs/whatsapp/cloud-api/...` (S7, S9) still resolves. The generic Graph API page (S1) and the Instagram page
  (S10) remain on `/docs/`. **The retry window differs between the old family (36 hours) and the new WhatsApp
  family (7 days)** — the divergence tracks the path split, which is suggestive but **not stated as a change**
  anywhere; no changelog entry for it was located in this pass.
- mTLS client certificate: the DigiCert-signed certificate expired **2026-04-15**; the replacement chains to a
  Meta-owned CA distributed as `meta-outbound-api-ca-2025-12.pem`, same CN `client.webhooks.fbclientcerts.com`
  (S1, corroborated by S14). Any installation that pins or verifies the client chain and has not loaded that CA is
  already broken as of today's date.
- **The SHA1 `X-Hub-Signature` header is not mentioned on any page read.** S1, S3/S4, S5 and S10 document only
  `X-Hub-Signature-256`. Whether SHA1 is still sent alongside, and whether its removal was announced, is
  **not stated / not checked** — do not assert either way.
- S13: two plausible URLs for a standalone "mTLS for webhooks" page both 404. If a later agent needs that page,
  find it by navigation from S1 rather than by guessing a path.

## 6. Ambiguities and gaps

1. **36 hours vs 7 days.** Two normative Meta pages give different retry windows for the same mechanism (S1/S10 vs
   S5/S6). Most likely a per-product difference plus a stale generic page, but **Meta does not say**, and neither
   page acknowledges the other. Any article must state the window per channel and cite the page.
2. **No response timeout outside Messenger.** 5 seconds is Messenger-only (S3/S4). WhatsApp, Instagram and the
   generic Graph page state none. Do not generalise the number; do design to it.
3. **Which bytes are signed.** S4 says the signature covers an escaped-unicode rendering with lowercase hex and
   that decoded bytes give a different result — while its own sample hashes the raw buffer. S5 says only "the JSON
   payload". **Meta never states "the raw request body" in so many words.** The safe implementation is to HMAC the
   exact bytes received without parsing or re-serialising; the documentation does not bless it explicitly.
4. **Constant-time comparison is never recommended.** Meta's samples use ordinary string inequality. Using a
   constant-time compare is strictly stronger than the documentation; it is not required by it.
5. **No deduplication key.** Every platform tells you to deduplicate and none tells you on what. For outbound
   status webhooks, the obvious candidate (`id`) is demonstrably insufficient on its own (S9: up to three statuses
   share one `id`).
6. **Ordering is undefined, not merely unguaranteed.** Only Messenger addresses it, and only for the outage case.
7. **`hub.challenge` type.** "an `int`" (S1, S4) vs "a random string" (S5). Treat it as an opaque string and echo
   it verbatim.
8. **mTLS enablement scope.** Per-WABA-subscription (S1) vs per-application (S5). Unresolved.
9. **Verification-failure retry behaviour.** Not stated whether Meta re-sends the handshake GET, how often, or for
   how long.
10. **Rejected-signature requests.** Not stated whether a 401 from signature validation enters the retry machinery
    or is treated as a delivery failure for alerting purposes.
11. **WhatsApp failure visibility.** No documented alert, no documented auto-disable, no documented delivery-error
    log. The `account_alerts` field is about account state, not webhook health.
12. **`account_alerts` payload shape is unverified.** S11 and S12 both returned navigation-only content to the
    fetch tool, so the exact field names could not be confirmed from a `/docs` page. Agent 028 or a follow-up
    should read S11 directly before any article names those fields.
13. **Override endpoint verification.** S8 requires a `verify_token` per override but does not say whether the
    `hub.challenge` handshake is performed against the override URL.

## 7. What Lynomia users would ask

- "I pasted the callback URL and Meta says it cannot be verified." → token mismatch, non-200, or the endpoint not
  echoing the challenge body; Meta will send nothing until it verifies (S5).
- "Verification worked but no messages arrive." → field subscription missing, app in Dev mode (S2, S6), or an
  override pointing elsewhere (S8).
- "Messages arrived hours late and out of order." → retry with decreasing frequency; ordering is not guaranteed;
  order by `timestamp` (S3/S4).
- "The same customer message was created twice." → retries and duplicate deliveries are expected; the endpoint must
  deduplicate (S1, S5, S6).
- "We were down for a day — do we get the messages back?" → inside the window, retries continue (36 hours or 7 days
  depending on the page); after it, notifications are dropped and **there is no API to fetch past webhook data**
  (S5).
- "Facebook/Instagram stopped delivering and never recovered." → 1 hour of failure unsubscribes the app from the
  Page/IG account; **resubscription is manual** (S3, S4).
- "We get `X-Hub-Signature-256` mismatches." → wrong App Secret for that app, or the body was parsed and
  re-serialised before hashing (S4, S5).
- "Our TLS is fine but Meta can't connect." → self-signed certificates are never supported (S1, S2, S5, S10); if
  mTLS/client-cert verification is on, the Meta CA bundle must be current (S1).
- "Where do we see that webhooks are failing?" → Messenger/Instagram: developer-account alerts. WhatsApp: nothing
  documented (S6).
- "Can each customer have their own webhook URL?" → per-phone-number and per-WABA overrides exist for messaging
  fields, but template and account-level fields always go to the app's default callback URL (S8).

## 8. Direct bearing on the Lynomia webhook path

Repository observations, for the orchestrator to route — not product changes.

| Lynomia behaviour | Evidence | Meta position |
|---|---|---|
| Handshake echoes the challenge via `render json: params['hub.challenge']`; mismatch returns `401` | `app/controllers/concerns/meta_token_verify_concern.rb:11-17` | Compliant. S5 accepts "anything other than status 200" for a mismatch. Rails' `json` renderer passes a `String` through unchanged, so the body is the bare challenge; the `application/json` content type is acceptable because **no page states a required content type** (framework behaviour, not a Meta claim) |
| Per-channel `webhook_verify_token`, with an installation-wide token for the app-level callback that has no phone number in the path | `app/controllers/webhooks/whatsapp_controller.rb:29-41` | Matches S8 exactly: template fields do not support overrides and always arrive at the app's default callback URL, so that URL legitimately needs its own token |
| Signature: `OpenSSL::HMAC.hexdigest('SHA256', secret, request.raw_post)`, prefix `sha256=`, compared with `ActiveSupport::SecurityUtils.secure_compare`; tries several candidate secrets | `app/controllers/concerns/meta_token_verify_concern.rb:6-7,33-39,42-44` | Algorithm, key and prefix match S1/S5.
