## 1. What the feature is

Zid is the third of four Commerce providers (`custom/app/services/commerce/providers.rb:3-4`). A Zid store is
connected by authorizing the installation's Zid app over OAuth 2.0 Authorization Code — no keys are typed
(`app/javascript/dashboard/i18n/locale/en/commerce.json` → `COMMERCE.SETTINGS.PICKER.ZID_HINT`, "Authorize the
{installationName} app on Zid. No keys to copy."). Once connected, Lynomia **reads** the store's customers and
orders through the Zid Merchant API (`https://api.zid.sa/v1`, `custom/app/services/commerce/zid/oauth.rb:5`),
caches them per conversation, and invalidates that cache from Zid webhook deliveries. Lynomia keeps no order
database (`custom/app/controllers/webhooks/zid_controller.rb:5-6`).

Zid is the only provider that offers both a native cart-abandonment event and a native cart-completion event, and
`Commerce::Zid::Webhooks::EVENTS` now subscribes to both (`custom/app/services/commerce/zid/webhooks.rb:12-13`:
`order.create`, `order.status.update`, `order.payment_status.update`, `abandoned_cart.created`,
`abandoned_cart.completed` — five, not three). Writes are limited to one action, `update_order_status`
(`custom/app/services/commerce/providers/zid/actions.rb:14`).

**Both Zid writes and Zid carts are hard-off in production.** `Commerce::Switches::PRE_UAT` lists `zid` under
both `:actions` and `:recovery` (`custom/app/services/commerce/switches.rb:16`), and `uat_cleared?`
(`switches.rb:39-41`) can only be overridden by the ENV-only `COMMERCE_ALLOW_PRE_UAT_PROVIDERS`, which the same
comment restricts to staging and simulated E2E. So no Super Admin switch can turn on Zid order actions or Zid
abandoned carts; it takes a reviewed code change. This is the single most important fact about Zid for
documentation, and the existing corpus states it correctly.

### OAuth flow as the code performs it

1. `ZidConnectionsController` checks, in order: `lynomia_commerce` on the account (`:30-32`, raises
   `Pundit::NotAuthorizedError`), `Commerce::StorePolicy#create?` (`:10`), `Commerce::Providers.enabled?('zid')`
   (`:34-36` → `PROVIDER_DISABLED`), and `Chatwoot.encryption_configured?` (`:18` →
   `ENCRYPTION_NOT_CONFIGURED`).
2. It issues a signed, account- and user-bound, single-use, 10-minute `Commerce::OauthState` and sets its nonce in
   an encrypted HttpOnly `SameSite=Lax` cookie scoped to the callback path (`:20-24`), then returns
   `{ authorize_url }`.
3. The browser is sent to `https://oauth.zid.sa/oauth/authorize` with `client_id`, `redirect_uri`,
   `response_type=code`, `state` (`custom/app/services/commerce/zid/oauth.rb:8-12`). The front end only follows a
   URL that passes `safeHttpsUrl` (`ZidConnectDialog.vue:32-33`).
4. The callback consumes the state **before** reading the code, deletes the cookie, and on an invalid state
   redirects to `/app` naming no account (`callbacks_controller.rb:12-14`). It then re-checks that the state's user
   is still an administrator of the state's account, that the account still has `lynomia_commerce`, and that Zid is
   still enabled (`:23-25`).
5. `Commerce::Zid::Oauth.token(grant_type: 'authorization_code', …)` is one form POST, never retried
   (`oauth.rb:16-20`, `http_client.rb:58-60`). The client secret travels only here.
6. Tokens are validated (`Commerce::Zid::Tokens.credentials`), then confirmed against
   `GET /managers/account/profile` (`oauth.rb:25-33`). **Nothing is saved before the profile succeeds**
   (`authorization.rb:13-18`).
7. Save under `Commerce::StoreLock('zid', <external_store_id>)`: a new store through
   `Commerce::StoreConnection#attach`, or re-authorization in place of this account's own store
   (`authorization.rb:18,26-41`).
8. `Commerce::Zid::WebhookRegistrationJob` is queued (`authorization.rb:19`).
9. The browser returns to `…/settings/commerce?zid=connected` or `?zid_error=<code>`
   (`callbacks_controller.rb:28,30,38-40`).

A merchant who installs the app from the Zid App Market without starting in Lynomia reaches the callback with no
state and connects nothing (`callbacks_controller.rb:12-14`; `docs/commerce/14-zid-oauth-and-tokens.md:60`).

### Tokens and scopes

Zid answers both grants with two distinct tokens plus a refresh token. `authorization` is sent as
`Authorization: Bearer`, `access_token` as `X-Manager-Token` — they are not interchangeable
(`custom/app/services/commerce/zid/oauth.rb:39-42`, `tokens.rb:3-6,10-14`). Stored keys: `authorization`,
`access_token`, `refresh_token`, optional `token_type`/`scope`, `expires_at` (nil when Zid sends no `expires_in`),
plus the Lynomia-generated `webhook_username`/`webhook_password` (`tokens.rb:8-22`; `webhooks.rb:25-26`). All of it
lives in `Commerce::Store#credentials`, which is `encrypts`-ed (`custom/app/models/commerce/store.rb:48`).

Zid tokens live about a year. `Commerce::Zid::TokenManager` refreshes `REFRESH_BEFORE = 60.days` early, backs off
`RETRY_AFTER = 1.hour` after a passing failure, and strips `TOKEN_KEYS` on `needs_reauth` — which deliberately
leaves the webhook pair in place for the next registration's cleanup (`zid/token_manager.rb:9-11`;
`commerce/token_manager.rb:110-116`). With no `expires_at`, the token is refreshed only after Zid rejects it
(`zid/token_manager.rb:15-19`). A refresh answered 200 with an unusable body goes straight to `needs_reauth` with
reason `refresh_response_invalid` (`zid/token_manager.rb:33`).

Scopes are fixed per app in the Zid Partner Dashboard; the authorize request carries none, so Lynomia cannot widen
them at runtime (`docs/commerce/14-zid-oauth-and-tokens.md:135`). The documented requirement is Orders read,
Webhooks read & write, and `abandoned_carts.read` for carts
(`custom/app/services/commerce/providers/zid/carts.rb:4`). The exact dashboard scope identifiers, and whether the
manager profile needs one of its own, are recorded as VERIFY (`14-zid-oauth-and-tokens.md:142-143`). Zid publishes
no readable list of granted scopes, so a refused write is detected only after the fact: a 403 on a status change
stamps `metadata['write_access'] = 'missing_scope'` until the store is re-authorized
(`providers/zid/actions.rb:10-11,55-58`; cleared at `authorization.rb:38`).

## 3. The webhook authentication contract, and the verification that was done

**Zid's mechanism is HTTP Basic Authentication, per webhook. There is no HMAC and no signing secret.** The body is
not signed (`custom/app/services/commerce/zid/webhook.rb:1-3`; `docs/commerce/15-zid-webhook-security.md:5-7`).

The deliberate verification the brief asks about is recorded in
`docs/commerce-production/02-provider-security.md:1-130`, and it found a real defect. Reading
`docs.zid.sa/create-a-webhook` on **2026-10-06** established that `POST /managers/webhooks` takes `username` and
`password` at the **top level**, alongside `event`, `target_url`, `original_id` and optional `conditions`
(`02-provider-security.md:27-39`). Lynomia had been sending a nested `authentication: { type: 'basic', username:,
password: }` object, which Zid does not define (`:19-24`). Consequences, as recorded at `:49-72`:

- Zid ignores the unknown key and registers the webhook **with no credentials**, returning an id — so registration
  reported success.
- Zid then delivers with no `Authorization` header, and `Webhooks::ZidController` refuses a credential-less
  delivery with 401 before parsing anything.
- Every Zid order event was silently lost; the only trace was the `commerce.webhook.rejected` metric, which looks
  identical to a misconfigured store.
- `docs.zid.sa/webhook-health-tracking` (read 2026-10-06) escalates this: a sliding one-hour window, DEGRADED at
  ≥10 failures, **BROKEN at ≥30 — at which point Zid stops dispatching entirely** and emails the partner; three
  retries per event at 1/5/15 minutes; HTTP 429 not counted; recovery requires the webhook UUID **and a new target
  URL** (`02-provider-security.md:76-88`).

Two conclusions were drawn and are now in the code. First, the payload sends `username`/`password` at the top
level, with **no compatibility fallback** — sending both shapes was considered and rejected
(`02-provider-security.md:92-99`; the reasoning is preserved verbatim in the code comment at
`custom/app/services/commerce/zid/webhooks.rb:58-69`). Second, the response check was untruthful: a `filter_map`
dropped any response without an id, so a store where two of three POSTs failed was recorded as registered with one
id. It now raises `INVALID_RESPONSE / zid_webhook_subscribe`, and the store's metadata is written only after every
event is subscribed (`webhooks.rb:40-50`; `02-provider-security.md:101-124`). Basic Auth also became **mandatory
for every Zid webhook on 2026-09-30** (Zid Partner changelog 57336), six days before that reading
(`02-provider-security.md:44-46`).

Also deliberately *not* done: no HMAC was invented for Zid, because Zid offers none
(`02-provider-security.md:177-180`).

Registration mechanics (`webhooks.rb:20-31`): under `Commerce::StoreLock('zid_webhooks', external_store_id)`,
`DELETE /managers/webhooks?original_id=<ZID_CLIENT_ID>` removes every subscription of the app in that store (404
treated as done, `:52-56`), a fresh pair is minted (`SecureRandom.hex(16)` / `SecureRandom.urlsafe_base64(48)`) and
**saved encrypted before any POST**, then each of the five events is subscribed to
`<FRONTEND_URL>/webhooks/zid/<external_store_id>` (`:75`). Delete-then-create makes re-authorization idempotent and
rotates the pair every time. Spec evidence for the top-level fields and the length floors:
`spec/services/commerce/zid/webhooks_spec.rb:24-32`.

Receipt (`custom/app/controllers/webhooks/zid_controller.rb:10-25`): the store id is read from
`request.path_parameters` only, because touching `params` would parse the JSON body before authentication
(`:11-13`); both halves of the pair go through `ActiveSupport::SecurityUtils.secure_compare` combined with
non-short-circuiting `&` (`zid/webhook.rb:12-13`); anything else is 401 plus a `commerce.webhook.rejected` metric,
and the body is never parsed. Deduplication is SHA-256 of the raw body per store, for one day, because Zid
documents no delivery id (`zid/webhook.rb:16-19`; `15-zid-webhook-security.md:62-67`). The body is sealed before it
reaches Sidekiq.

Four things about the delivery side remain unverified against a real store
(`15-zid-webhook-security.md:96-103`): whether Zid echoes the credentials in `GET /managers/webhooks`, whether
`order.payment_status.update` is a subscribable event name at all, whether a delivery carries a usable delivery id,
and the delivery body shape. The cart envelope is unverified separately — see §5.

Two assumptions in the cart path are explicitly unverified and confined to one file
(`providers/zid/cart_events.rb:8-18`): **cart identity** — Zid's schema carries `id`, `cart_id` *and*
`session_id`, and does not say which is stable, so `IDENTITY_KEY = 'id'` is the single declared choice and a
payload without it is refused rather than falling back (`:10-14,20,62-70`); and the **webhook envelope** — Zid
publishes the abandoned-cart object but not the delivery envelope, so the resource is read from the top level or
one of `abandoned_cart`/`cart`/`data`, and anything else is refused (`:16-18,21,62-68`). Routing is by event name
only: a cart-shaped body with no event name is treated as an order event rather than guessed at
(`cart_events.rb:28-33`; `zid/webhook_job.rb:8-10,19`), and a cart delivery Lynomia cannot place is logged as
`unusable_zid_cart_delivery` with a `commerce.cart.unusable_delivery` metric (`zid/webhook_job.rb:39-45`).

## 7. Failure paths

1. **The registration defect, historically.** Until `02-provider-security.md`'s fix, every Zid order event was
   lost silently and a busy store would have reached Zid's BROKEN state within an hour, after which a corrected
   registration alone would not resume delivery (recovery needs a new target URL). Any earlier impression that
   "Zid realtime works" was about the 120-second polling, not webhooks
   (`01-provider-capability-matrix.md:104`).
2. **Partial registration.** `subscribe` now raises on the first event without an id, so the store keeps a freshly
   minted pair, has fewer than five subscriptions at Zid, and no `metadata.zid_webhooks` record
   (`webhooks.rb:27-28,44-50`). `Commerce::Zid::WebhookRegistrationJob` retries only
   `STORE_UNAVAILABLE / TIMEOUT / RATE_LIMITED` and otherwise reports once to the exception tracker
   (`zid/webhook_registration_job.rb:5,12-16`). Nothing in the UI shows that a store's webhooks are incomplete;
   the store keeps working on polling.
3. **Re-authorizing a *disabled* Zid store drops its webhook pair and nothing re-registers it.** `reauthorize`
   replaces `credentials` wholesale with the new token hash, which has no `webhook_username`/`webhook_password`
   (`authorization.rb:37`; `tokens.rb:10-14`); `Commerce::Zid::WebhookRegistrationJob` runs
   `if store&.active?` and so skips a store that stays disabled (`zid/webhook_registration_job.rb:11`;
   `authorization.rb:36-37`); and a later Enable calls `register_webhooks`, which is a no-op for Zid because
   `registers_webhooks?` is the base `false` (`store_connection.rb:63,120-122`; `providers/base.rb:52-56`).
   Zid's existing subscriptions keep delivering with the old pair, every delivery gets 401, and Zid's health
   tracker marks the webhook DEGRADED at 10/hour and BROKEN at 30/hour. The user-visible trace is nothing at all.
   Code-verified; **not** observed on a live store.
4. **Token lapse.** Zid's own guidance is to refresh around month 10 and the 60-day window applies only on use,
   so a store unused for ~10 months lapses; there is no background sweep
   (`14-zid-oauth-and-tokens.md:132`). It surfaces as `needs_reauth` and Reconnect fixes it.
5. **Uninstall.** The merchant uninstalling the app at Zid invalidates every token; Lynomia learns only on the
   next read → 401 → refresh `invalid_grant` → `needs_reauth` (`14-zid-oauth-and-tokens.md:131`). Zid's uninstall
   event is not subscribed, so there is a window where the store looks Active.
6. **Rate limit.** 60 requests/min per app and store; after a 429 or zero remaining, further calls fail fast for
   up to 60 s and the panel serves its cache (`providers/zid.rb:12-13`; `backoff.rb:13-16`).
7. **Lost answer on a status change.** `write_json` is sent once; a lost answer raises `TIMEOUT /
   unknown_outcome` (`http_client.rb:69-71,117-126`) and is settled by `reconcile`, which only reads
   (`actions.rb:46-51`, `SETTLED_AFTER = 5.minutes`).

## 11. Arabic / Gulf-market notes

Zid is a Saudi platform and the Arabic surface matters more here than for any other provider.

1. **The UI says "زد"; the documentation says "Zid".** `ar/commerce.json` renders the provider name as `زد`
   throughout — `COMMERCE.PROVIDERS.ZID = 'زد'`, `COMMERCE.SETTINGS.ZID.CONNECT = 'الربط مع زد'`,
   `PICKER.ZID_HINT = 'امنح تطبيق {installationName} الصلاحية من زد…'`. The Arabic article keeps the Latin form:
   title `ربط Zid`, step 2 `**الربط مع Zid.**` (`ar/connect-zid.md:2,24`). A merchant following the Arabic article
   is told to click a button whose label does not match. One of the two has to move, and per the branding rule the
   product name should be decided once and added to the Crowdin glossary as non-translatable if it stays Latin.
2. **Time zone defaults to `Asia/Riyadh`.** `Commerce::Providers::Zid::Normalizer::DEFAULT_TIME_ZONE =
   'Asia/Riyadh'` (`normalizer.rb:23,26`), used when the Zid store profile carries no `timezone`. Zid sends order
   timestamps as `"YYYY-MM-DD HH:MM:SS"` with no zone (`normalizer.rb:13`), so an order's displayed time depends
   on the store profile — worth saying in an Arabic article aimed at GCC merchants outside Saudi Arabia (Kuwait,
   UAE), whose orders would otherwise read in Riyadh time.
3. **Courier names prefer English over Arabic.** A Zid courier can be `{ name: { ar, en }, code }`, and
   `normalizer.rb:102-106` takes `name['en']` first, falling back to `name['ar']`. An Arabic-speaking agent sees
   the English carrier name whenever Zid supplies both. That is a product decision to document (or revisit), not
   a bug — but it is invisible today.
4. **Saudi mobile normalization.** Zid sends mobiles as international digits with no `+` (e.g. `966500000006`);
   `normalizer.rb:134-139` prefixes `+` when the value matches `/\A[1-9]\d{7,14}\z/` before E.164 normalization.
   Matching is exact on E.164, so an Arabic-language article explaining "why my customer isn't matched" needs to
   say the contact's number must be in international form.
5. **Masked values.** Zid masks names, emails and phones (`"J*** D***"`, `"t***@…"`, `"***00"`), and any value
   containing `*` is never treated as an identifier (`normalizer.rb:10-11,129-139`; carts `carts.rb:6-7`). This is
   covered in both locales (`ar/connect-zid.md:55-56`) and is one of the more common Gulf-market support
   questions.
6. **Marketplace orders.** `is_marketplace_order` means no customer, so the order can never be linked
   (`normalizer.rb:43-45`). Covered in both locales.
7. **Currency.** Zid's `currency_code` is required and passed through unchanged (`normalizer.rb:34`); amounts are
   decimal strings (`:153-155`). Nothing formats SAR specially, and nothing in the corpus claims otherwise.
8. **RTL.** No Zid-specific RTL handling exists or is needed in the connect flow — `ZidConnectDialog.vue` uses
   only the shared `Dialog`, `Button` and `DocsLink` components and Tailwind logical utilities.
