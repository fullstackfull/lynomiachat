# Lynomia Flow Builder: end-to-end tests

Two E2Es on the working tree, Ruby 3.4.4 / Node 24 verification image, production configuration. Results are committed
in `e2e/results/`, screenshots in `screenshots/`.

## WhatsApp: scenarios A–E (26/26)

`e2e/whatsapp.sh` → `e2e/check_flows_whatsapp.rb`, on a fresh harness database seeded by the staging harness
(`docs/chatwoot-upgrade/staging-harness`: Tenant A's WhatsApp Cloud number, Tenant B).

| Real | Simulated |
|---|---|
| the flows API (created, saved, published as Tenant A's administrator); Chatwoot's WhatsApp webhook endpoint with Meta's signature; the incoming message service; conversations, the bot phase and `bot_handoff!`; the flow runtime and its lock; Chatwoot messages and `SendReplyJob` through the WhatsApp Cloud provider; `ActionService`; Commerce's WooCommerce provider against the **disposable local test store** (customer 2's orders, never a merchant store; nothing written); Chatwoot's webhook delivery and `SafeFetch` | Meta (FakeGraph, in process: the payloads the provider sends are recorded); the customers (signed webhook payloads); n8n (a local HTTP catcher on 127.0.0.1). Jobs run inline; scheduled jobs (timeouts) are recorded |

| # | Check |
|---|---|
| A1–A2 | the welcome menu goes out as WhatsApp reply buttons with ids `lfb:menu:track`, `lfb:menu:care`; the conversation is in the bot phase |
| A3 | a tap follows the option id: the order number is asked |
| A4 | the customer's own order #18 is found in the WooCommerce store: "Order #18 is refunded." |
| A5 | the session completes; the conversation stays with the flow |
| A6 | **order #26, another customer's, is not disclosed**: not found, then handed to a human |
| A7 | after the handoff the bot stays silent |
| A8–A9 | Customer care: the Customer Care team assigned, the conversation opened, the reason left as a private note that never goes to WhatsApp |
| B1–B4 | Arabic: a WhatsApp list with the Arabic text, the node's button label `القائمة` and row ids; a row reply follows its id; English: the English list with `Menu`; a typed option number is accepted |
| C1–C2 | a contact in the shared VIP audience gets the VIP branch and the `vip` label; another gets the regular branch |
| D1–D3 | a question asked with its timeout scheduled; a wrong answer asked again with the retry text; `٤٥٦` stored in the contact's `order_ref` number attribute as 456 |
| D4–D5 | an agent's reply hands the waiting session to humans (`human_reply`); the bot does not answer afterwards |
| E1 | as shipped, SafeFetch refuses the private n8n address; the flow goes on without waiting |
| E2–E3 | self-hosted n8n (private network allowed) receives one POST signed with the flow bot's secret, with the flow, the conversation and the reply |
| T1–T3 | another account's administrator cannot read the flow; a flow naming another account's team cannot be published; every message the flow sent is a Chatwoot message (one per Graph call) |

**Real WhatsApp UAT limit**: Meta is simulated. A live run needs a WhatsApp Cloud number connected to a Lynomia staging
account and a test phone: send "hi" to the number, tap the buttons, check delivery in Chatwoot. The payloads asserted here
are the ones Chatwoot's provider sends to Meta, so the remaining risk is Meta's acceptance of them (interactive button and
list payloads are Chatwoot's existing ones; the List button label is the only new field, within Meta's 20-character
limit).

## Builder (17/17)

`e2e/run.sh` → `e2e/e2e_builder.js` (Playwright, Chromium), against the production build on the plain server.

| # | Check |
|---|---|
| 1–2 | Flow Builder in Settings; a new flow opens on a Start → End starter |
| 3 | a Buttons node shows one connector per option (2 options + `other` + `timeout`) |
| 4 | saving a half-built draft shows the server's validation (unconnected options named by their titles, unreachable nodes) |
| 5 | outputs wired by dragging from connector to node |
| 6–7 | the flow publishes once valid; the draft became version 1, published |
| 8 | the WhatsApp inbox is connected (Chatwoot's set_agent_bot) |
| 9–12 | Test Mode: the menu with its buttons; tapping Track order follows its option; Customer care hands off with the note; no session kept |
| 13 | the session inspector opens |
| 14 | Arabic: right to left, translated nodes, nothing falsely unsaved |
| 15 | phone width: no page-wide horizontal scroll |
| 16 | no browser errors, no 5xx from the flows API |

Found and fixed by this E2E: a new canvas opened zoomed in to 2× (the view now fits at most 1×); "Unsaved changes"
appeared after loading, because Vue Flow adds its own fields to the nodes (now the graph itself is compared); Arabic output
labels were clipped by their connectors; the palette took the whole phone screen (now hidden below `md`, panels open over
the canvas).
