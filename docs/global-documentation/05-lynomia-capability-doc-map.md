# 05 — The Lynomia capability map

Every user-facing product area, the code behind it, and the limits a reader must be told about. Built by reading
`app/`, `enterprise/` and `custom/` rather than by trusting the phase documentation — and the places where those two
disagree are listed first, because each is somewhere a writer would otherwise publish something false.

This document is the **accuracy gate** for the corpus: an article may not claim anything this map does not support,
and §3 is the list of things that must never be claimed at all.

---

## 1. Where the existing documentation is out of date

Documentation capability map for /home/user/lynomiachat (Lynomia Chat — a Chatwoot 4.18 fork with `enterprise/` EE overlay and a large Lynomia-only `custom/` tree; resolution order Custom → Enterprise → base via `ChatwootApp.extensions`, lib/chatwoot_app.rb:40-48). 41 user-facing areas below, each verified against app/, enterprise/ and custom/ rather than against the phase docs.

WHERE THE DOCS AND THE CODE DISAGREE — the code wins, and these are the five places a writer would otherwise publish something false:

1. docs/product-enablement/00-platform-capability-map.md §4.8 says WhatsApp templates are "one jsonb column … no templates table, no template model", editing is "Absent in every tree", and Graph API "v14.0 is hardcoded". All three are now wrong. `whatsapp_message_templates` exists (db/schema.rb:1768, custom/db/migrate/20261005100000), `Whatsapp::MessageTemplate` is a real audited model, create/edit/delete/submit/duplicate all exist (custom/app/controllers/api/v1/accounts/whatsapp/message_templates_controller.rb), and `Whatsapp::FacebookApiClient::DEFAULT_API_VERSION` is `v24.0` (app/services/whatsapp/facebook_api_client.rb:7). The map predates the P3 Template Manager phase.

2. Same map §4.9 says "there is no Audience list page at all". There is: route `contacts_dashboard_audiences_index` → AudiencesIndex (app/javascript/dashboard/routes/dashboard/contacts/routes.js:49), reachable from Sidebar → Contacts → Segments → All Audiences (Sidebar.vue:556-560).

3. Same map §4.2 defect 1 says `event_name` is unvalidated and an arbitrary value saves silently. Fixed: `AutomationRule#event_names` plus an inclusion validation (app/models/automation_rule.rb:40,54-58).

4. Same map §4.12/§6 flags an unreserved global portal-slug namespace as a standing incident risk. Fixed: `Portal::RESERVED_SLUGS` (app/models/portal.rb:39-40) and `platform_owned` portals with `account_id` nullable (custom/db/migrate/20261005110000).

5. Same map §4.13 says Super Admin "cannot see or manage Portals, Categories or Articles at all". It now can, for platform-owned content only (config/routes/documentation.rb, custom/app/controllers/super_admin/{portals,categories,articles}_controller.rb).

WHAT IS STILL TRUE AND MUST GOVERN EVERY COMMERCE ARTICLE: `Commerce::Switches::PRE_UAT = { actions: %w[salla zid shopify], recovery: %w[salla zid shopify] }` (custom/app/services/commerce/switches.rb:16) and WooCommerce has no `RECOVERY_KEYS` entry (:15). So in a default production install, order actions work for WooCommerce only and abandoned carts / recovery work for nobody. `COMMERCE_ALLOW_PRE_UAT_PROVIDERS` is ENV-only and explicitly staging-only. Commerce automation is also read-driven, not webhook-driven: `Automation::CommerceEvents.dispatch` has one call site (custom/app/models/commerce/contact_metric.rb:27), reached only from `Commerce::Realtime` and `Commerce::ConversationPanel`, so a commerce rule fires when something re-reads the store — in practice when an agent opens the conversation panel. The only scheduled commerce job is `Commerce::ActionSweepJob` (config/schedule.yml:82); there is no polling.

THE OTHER CROSS-CUTTING LIMITATION: the platform documentation centre is built but not wired into the product. `/docs`, `/docs/:slug` and `/changelog` resolve platform portals (custom/app/controllers/documentation_controller.rb) and Super Admin authors them, but every in-product "Learn more" link still points at `chwt.app` or `chatwoot.com` (app/javascript/dashboard/helper/featureHelper.js:2-29) and the sidebar changelog card still fetches the external hub feed (app/javascript/dashboard/api/changelog.js). Nothing in the dashboard links to `/docs`. Writers should not promise contextual help.

## 3. What must never be claimed

This is the most important list in the document. Each line is something a reader could reasonably assume, that this
product does **not** do. An article that implies otherwise is a defect.

- Abandoned-cart detection as a durable feature: there is NO cart table (the four commerce tables are commerce_stores, commerce_customer_links, commerce_contact_metrics, commerce_action_runs), no cart migration, no provider-neutral 'cart became abandoned' transition, no commerce cart event, no cart condition and no cart flow node. A cart is a transient Data.define cached in Redis only, and the cache is deleted (not staled) on any webhook.
- Automatic, push-driven commerce events: provider webhooks only signal 'this customer changed' and their payload is discarded; there is no polling job. Do not write an article promising real-time commerce automation.
- Salla order write actions of any kind (supports_actions? is false — no status change, no cancel, no refund, no resend).
- A Salla `paid` payment status, and therefore commerce_order_paid events and any spend figure for a Salla-only contact.
- Salla order lookup by order number (searches_orders? is false).
- WooCommerce shipped and delivered order statuses, shipment data, tracking numbers, abandoned carts and recovery — so commerce_order_shipped and commerce_order_delivered can never fire for WooCommerce.
- Shopify order status changes and invoice/payment-link resend (Shopify has no order status to set).
- Zid cancel and refund actions (Zid refunds are reverse orders).
- HMAC signature verification on Zid webhooks — authentication is HTTP Basic with a per-store random credential pair.
- A 'Conversation Workflow' engine, model, table, service or state machine. The name exists only as a route, a components-next folder, a sidebar label and a Swagger tag; the page renders auto-resolve plus required attributes.
- Any business-hours, time-of-day or working-hours condition in the automation or flow rule engine — out-of-hours handling cannot be built.
- Any priority escalation level or escalation engine (an explicit TODO in the Captain handoff tool).
- Flow entry from a store event, a schedule, a webhook or a campaign — flows are entered from a conversation message only.
- Flow Builder support for any channel other than WhatsApp Cloud (website, email, Twilio, SMS, Instagram, Facebook, Telegram, Line, TikTok are all rejected).
- A flow template, bot template or recipe catalogue on the server: no recipes table, endpoint, model, service, job or seeder anywhere in app/, enterprise/, custom/ or lib/.
- Any telemetry on any starter, recipe, template or flow-template path (grep for useTrack/analytics over app/javascript/dashboard/recipes returns zero), and on a community install no Super Admin path exists to enable telemetry at all.
- Article revision or version history — Article is not an audited model, and the draft buffer is a single slot.
- Help Center folders as a usable feature: the folders table, Folder model and articles.folder_id exist with no controller, route, policy, serializer or UI.
- Help Center portal members: the portals_members join table exists with no model and no association.
- Bulk contact operations beyond add-labels, remove-labels and delete — no bulk block, bulk merge, bulk company, bulk campaign or bulk add-to-audience.
- Adding chosen contacts to a shared audience: an audience stores only a query, membership is recomputed, there is no membership table and no `id` contact filter key, so 'id in (a set)' is not expressible. Use a label.
- An audiences table, audience_members table, audience_contacts table or segments table — none of the 108 tables is one.
- A guard that stops a shared audience being deleted or unshared while a flow graph references it (Audience::Usage checks only automation rules and active/processing one-off campaigns).
- A third campaign type: the enum is exactly { ongoing: 0, one_off: 1 } — no recurring-scheduled and no abandoned-cart campaign type.
- Creating a WhatsApp template from Meta's Template Library (`library_template_name` appears nowhere).
- A WhatsApp template quality-score, quality-rating or health dashboard — quality_score is kept verbatim inside meta_payload and is surfaced nowhere; the message_template_quality_update, _components_update and template_category_update webhook fields are not subscribed, handled or routable.
- Editing a WhatsApp template's name or language after creation (Meta does not allow it; update silently ignores both).
- WhatsApp catalogue, carousel and list template components — Lynomia Chat cannot send them.
- WhatsApp history import and contact backfill for Business-App coexistence numbers: no `history` or `smb_app_state_sync` subscription or handler exists, and Meta only permits it within 24 hours of onboarding.
- Any Evolution / 'WhatsApp QR' channel, service or provider — docs/whatsapp-qr/ is paused fallback research only and no code exists.
- A custom-role permission for inboxes, channels, campaigns, WhatsApp templates, flows, automation rules or audiences — the 7 permissions are conversation_manage, conversation_unassigned_manage, conversation_participating_manage, contact_manage, report_manage, knowledge_base_manage, commerce_order_manage. Everything else is administrator-only.
- A working `sla_policy_id` automation condition — it is accepted by the EE attribute list but has no filter_keys.yml entry, no SQL branch and no UI, and a rule using it auto-deactivates.
- Any in-product link to /docs, /docs/:slug or /changelog, and any contextual-help registry: every 'Learn more' still points at chwt.app or chatwoot.com, and the sidebar changelog card fetches the external hub feed, not the platform changelog portal.
- A commerce report, campaign report, flow report or starter-usage report.
- Lynomia endpoints in the published OpenAPI spec: /flows, /commerce/*, /whatsapp/message_templates, /campaigns/audience_preview, /billing, /platform/api/v1/billing and /api/v1/mobile/auth are all absent from swagger.json, which is still titled 'Chatwoot' and points at app.chatwoot.com.
- A macro action that touches custom attributes or Commerce, and a buildable `change_status` macro action (API-only).
- A duplicate, copy, clone or version endpoint for a WhatsApp template at Meta — Meta does not support one; custom/app/services/flows/template.rb is a flow-side reader of synced templates, not a versioning feature.
- A billing plan limit beyond agents, inboxes and stores; and any ability for a plan to grant a premium (EE) or system feature.
- A payment processor other than Stripe.

## 4. How this was used

- Every article in the corpus was written against this map, and every article was re-read against §3 before

- The areas marked **do-not-document** in §2, and the whole of §3, are the reason several obvious-looking articles do
  not exist. That is a decision, recorded here, and not an omission.
- Where an area is flagged pre-production, the article says so in its own words rather than describing the feature as
  if it were finished.
