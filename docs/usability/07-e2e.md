# Browser journeys

Real Chromium, real components, real stylesheet, real strings, **English and Arabic**, **1280×900 and 390×844**.

```
docs/usability/e2e/run.sh [out_dir]
```

**16 journeys · 38 checks · 0 failed · 24 screenshots.** Results in
[`e2e/results/journeys.json`](e2e/results/journeys.json), log in `e2e/results/journeys.log`, screenshots in
`e2e/results/screenshots/`.

## 1. How it runs, and what that does and does not prove

The earlier phases' end-to-end suites boot the Rails application in Docker against a seeded database. **This
container has no Docker daemon, Ruby 3.3.6 against a Gemfile that wants 3.4.4, and no running Postgres**, so that
harness cannot run here. Rather than claim a run that did not happen, this phase uses a different harness with an
honest boundary:

`docs/usability/e2e/harness/` is a small Vue application built by Vite that mounts **the real components this phase
changed** — `ContactMoreActions`, `RecipeDialog`, `RecipeInputs` and the three real catalogues — with the dashboard's
**real** stylesheet (`assets/scss/app.scss` through the project's own Tailwind configuration), the **real** English
and Arabic message files, a **real** `vue-router` carrying the route records whose `meta` gates the cross-module
actions, and the i18n instance created the way the dashboard creates it (on `en`, then switched), so a key Crowdin has
not translated yet falls back to English exactly as it does in the product.

Replaced by fixtures: the Vuex store, `useAccount`, `usePolicy`, `useAdmin`, the Commerce options loader and
`useAlert`. One account: a WooCommerce store, SAR and AED, three teams, a `vip` label, one shared audience
(referenced by two rules and one scheduled campaign) and one personal filter.

| Proven here | Not proven here |
|---|---|
| the components render, mirror and fit at both widths | that Rails serves the pages |
| the menu, gallery and wizard behave, and what they emit | that the create calls reach the server |
| permission and shared/personal gating of the cross-module actions | server-side policy (covered by the Ruby suites, unchanged) |
| the payloads the recipes build | that the server accepts them (covered by the catalogue specs, which transcribe its contracts) |
| click counts, keyboard focus, accessible names, direction, overflow | the whole-page navigation between modules |

The whole-page journey — the prefill query arriving at the Automation panel and the Campaign dialog — is covered by
`settings/automation/specs/Index.spec.js` and `campaigns/pages/specs/WhatsAppCampaignsPage.spec.js`, not by the
browser run. The gap is recorded here rather than papered over.

Those two specs each caught a real defect while being written, which is worth recording:

- the Automation page first read the audience from a `watch(..., { immediate: true })`. An immediate watcher runs
  **during setup**, before template refs exist, so `addDialogRef.value` was still null and the panel never opened.
  It reads the query in `onMounted` now, which is right for that page because `SettingsWrapper` keys it by the
  route's full path and remounts it when the query changes.
- the Campaigns page first read it in `onMounted`. That page is **kept alive** by `CampaignsPageRouteView` and is
  never mounted a second time, so coming back to it with another audience did nothing. It reads the query in
  `onActivated`, which also runs on the first render; the spec exercises deactivation and re-activation to prove it.

## 2. The journeys

Clicks are counted by the runner: a pointer action is one, and a `select` choice is one. Nothing is estimated.

| Journey | Measured | What it replaces |
|---|---|---|
| **A** · open a shared audience's menu and choose "use it in a new rule" | **2 clicks** | leave the audience → Settings → Automation → Add → event → change the default condition's attribute → scroll to the Audience group → operator → find it **by name**: ≈11 clicks and a name lookup |
| **B** · a personal audience's menu | — | it offers the duplicate and the link, and **neither** cross-module action, because neither module may reference a personal filter |
| **C** · "high-value buyers" from a preset | **4 clicks** to the built conditions, +2 for the name-and-share dialog | Filter → attribute picker → Commerce group → Visible spend → operator → amount → Apply → Save → name → share → Save: ≈11 clicks, after knowing the field model |
| **D** · "order tracking bot" from a template | **4 clicks** | New flow → name → create → 12 palette clicks → ≈25 fields → 19 edge drags: ≈59 interactions |
| **E** · "customer with an open order" from a recipe | **4 clicks** | Add → event → attribute → Commerce group → operator → value → add action → assign team → team → Save: ≈15 clicks, and the rule saves **active** |

Each runs four times: English and Arabic, desktop and 390px. The counts are identical in all four.

## 3. The checks

All 38 pass. By group:

**Content and gating**

- the Audience section offers both cross-module actions, the duplicate, the link and the preset shortcut;
- what already references the audience ("Used by 2 automation rules · 1 campaign") is visible **where the audience is
  acted on**, not only inside the condition editor;
- a **personal** audience offers neither cross-module action, and still offers the duplicate.

The permission case — an **agent** being offered neither, because the target routes refuse them — is not one of these
38: it is asserted in `ContactMoreActions.spec.js`, which drives the same gate with the policy swapped.

**What the recipes build**

- the audience preset builds `commerce_spend_sar is_greater_than 1000` for the currency chosen;
- the flow template produces **12 nodes and 19 edges** with the chosen team on its handoff;
- the automation recipe arrives with `active: false` and carries its condition and the chosen team.

**Accessibility**

- the overflow button has an accessible name (`aria-label`, which it did not have before this phase);
- it takes focus from `Tab`;
- `Enter` opens the menu.

**Direction and layout**

- `direction` resolves to `ltr` in English and `rtl` in Arabic — including the dialog, which teleports to `<body>`
  and takes its direction from the `accounts/isRTL` getter rather than from the DOM;
- **no horizontal overflow** at 1280px or at 390px, in either direction.

## 4. Screenshots

24, at `e2e/results/screenshots/`: `journey-<a|c|d|e>-<surface>-<en|ar>-<desktop|390px>.png`. Functional evidence,
not a design pass.

What they show:

- the audience menu with its two sections and the usage line;
- the three galleries, Commerce entries first because the fixture account has a connected store;
- the wizards with their account-specific pickers;
- in Arabic: the dialog mirrored, labels right-aligned, Cancel and Create swapped, the number input right-aligned;
- at 390px: the cards stack, the buttons stay reachable, nothing is cut off.

One honest observation in the Arabic screenshots: the strings added by this phase render **in English**, because
only `en.json` was updated — the repository's rule for product strings, with other languages handled through Crowdin.
That is the product's real behaviour for a new string, and the layout around it is correctly mirrored. Latin
sentences inside an RTL paragraph put their full stop on the left; that is standard bidirectional rendering and
resolves itself once the strings are translated.
